# QR受付の高速化と実測

目標: QR認識から「受付OK」の表示まで、通常の通信条件で p95 が 1,000ms 以下。**DBに確定する前に成功を表示しない**（成功表示は `/api/checkins` の応答後）。

## 実施した最適化

| 対象 | 内容 |
|---|---|
| カメラ起動 | 受付画面を開いている間はカメラを起動したまま（連続受付で再起動しない）。背面カメラ・1280x720を指定 |
| QR検出 | 対応ブラウザ（Android Chrome等）は標準の `BarcodeDetector` を使用（約60msごと）。非対応（iPhone Safari等）は `@zxing/browser` を40ms間隔で走査 |
| 重複スキャン | 同じQRの3秒以内の再検出は無視。通信中は検出をロック |
| 連続受付 | 「受付OKのあと自動で次へ」（既定ON、1.4秒後）。音・振動のフィードバック |
| トークン検証 | HMAC検証後、チケットを1回のクエリで取得（参加者・イベント・担当スタッフ・受付済みを同時に取得） |
| API | 認証（セッション確認）とリクエスト本文の読み取りを並行。権限確認は取得済みのイベント情報で行い、追加クエリなし（従来は権限確認のためにチケットを再取得していた） |
| DB更新 | 入金済みの受付は通常の分離レベルで、受付の一意制約（`Checkin.ticketId`）で二重受付を防止。入金処理を伴うときだけ Serializable |
| 計測 | 画面に直近50件の p50/p95/最大（検出→結果表示）を表示。APIは `Server-Timing: checkin;dur=…` を返す |

## 実測結果

### サーバー処理のみ（ローカルDB・自動テスト）

`tests/integration/checkin.test.ts` の連続25名（QR・受付コード・検索の混在）:

- n=25 / p50 = 2.0ms / p95 = 2.4ms / 最大 2.6ms / 成功率 25/25
- 同一チケットへの同時受付（QR・受付コード・検索・QR再送の4並行）: 受付成功は常に1回（二重受付防止率 100%）

※ ローカルの使い捨てPostgreSQLでの値。**本番（Neon＋Vercel）の値ではない**。本番ではDBまでの往復（東京リージョン内で数ms〜数十ms/クエリ）と、サーバーレスのコールドスタート（初回のみ数百ms〜）が加わる。

### 実機・本番環境（未実施）

**iPhone Safari・Android Chrome の実機での計測は未実施。** 「1秒以内を達成した」とは報告できない。次の手順で実測する:

1. 本番反映後、テスト用イベント・テスト参加者（20名以上）を用意する（本番の参加者を使わない）。
2. 受付端末（iPhone Safari、Android Chrome の両方）で `/checkin` を開き、QRタブで連続して読み取る。
3. 画面下の「直近N件: p50 / p95 / 最大（検出→結果表示）」を記録する。
4. サーバー側の値は、ブラウザの開発者ツール（Network）で `/api/checkins` の `Server-Timing` ヘッダーを確認する。
5. p95 が 1,000ms を超える場合の切り分け: `Server-Timing` が大きい→DB/コールドスタート、小さい→通信またはカメラ検出。

## 受付コード・参加者検索の運用

- 受付コード（6桁）は、マイチケット画面・QRチケット画面・メールに表示される。受付画面の「受付コード」タブで入力すると6桁で自動的に確定する。
- 入力ミスが15回/10分続くと、その担当者は一時的にロックされる。
- 参加者検索は、氏名・かな・チケット番号で検索し、同姓同名がいる場合は「電話番号の下4桁（本人に言ってもらう）」か「身分証」で確認する。確認方法は受付記録（`Checkin.verification`）と監査ログに残る。
